# AGENTS.md

## Назначение

Этот файл - рабочий манифест для AI-агентов и разработчиков, которые меняют код
в этом репозитории. Он дополняет `README.md`: README объясняет проект людям,
а `AGENTS.md` фиксирует ожидания к агенту, стилю кода, проверкам и безопасным
границам изменений.

Относись к этому документу как к живому соглашению. Если агент или разработчик
повторяет одну и ту же ошибку, добавь сюда короткое правило, которое поможет не
повторять ее снова.

## Контекст проекта

- Это production Telegram-бот для Bikes.
- Основной стек: Python 3.14, aiogram 3, SQLAlchemy 2 async, asyncmy,
  pydantic-settings, loguru, APScheduler.
- Основной код лежит в `app/`, тесты - в `tests/`, документация - в `docs/`.
- Конфигурация проекта, линтеров и типизации находится в `pyproject.toml`.
- Makefile сейчас содержит команды `make install`, `make run`, `make lint`,
  `make format`.

## Манифест хорошего Python-кода

- Читаемость важнее хитрости. Выбирай простой код, который легко проверить и
  поддерживать через полгода.
- Явность лучше неявности. Не прячь важную логику в магии, глобальном состоянии,
  неочевидных сайд-эффектах или слишком умных декораторах.
- Стиль должен быть единым. Следуй настройкам `ruff` и `mypy` из `pyproject.toml`;
  PEP 8 важен как инструмент читаемости, а не как самоцель.
- Типизация должна помогать. Пиши понятные type hints, сохраняй строгую типизацию
  и не ослабляй проверки без веской причины.
- Маленькие функции лучше длинных сценариев. Функция должна делать одну понятную
  вещь, а класс - представлять одну устойчивую концепцию.
- Побочные эффекты держи на краях системы. Бизнес-логику отделяй от Telegram API,
  базы данных, файловой системы, планировщиков и внешней сети.
- Зависимости передавай явно. Не добавляй скрытые синглтоны и новое глобальное
  состояние, если можно использовать существующие слои конфигурации, middleware
  или явные параметры.
- Ошибки должны быть видимыми. Не глотай исключения молча, не возвращай `None`,
  если это маскирует проблему, и логируй контекст без секретов.
- Асинхронный код не должен блокировать event loop. Для операций ввода-вывода
  используй async-интерфейсы и существующие паттерны проекта.
- Архитектура должна соответствовать размеру задачи. Не добавляй слои, фабрики
  или абстракции ради абстракций; добавляй их только когда они реально уменьшают
  сложность или совпадают с уже принятым стилем.
- Тестируемость - критерий качества дизайна. Если изменение трудно проверить без
  большого количества моков, сначала упрости границы ответственности.
- Безопасность включена по умолчанию. Не коммить секреты, не логируй токены и
  персональные данные, валидируй внешние данные и используй параметризованный
  доступ к БД.

## Рабочие правила для агента

- Перед изменениями прочитай ближайший существующий код и следуй его стилю.
- Делай минимально достаточные правки в рамках задачи. Не проводи попутные
  рефакторы без явной необходимости.
- Не откатывай и не перезаписывай чужие незакоммиченные изменения.
- Не трогай `.env`, `logs/`, кэши и сгенерированные артефакты без прямого запроса.
- Для человекочитаемой документации в этом проекте предпочитай русский язык,
  если рядом уже используется русский.
- Если меняешь поведение, обнови тесты и, когда нужно, документацию в `docs/`.

## Команды

Проект требует Python 3.14. Если системный `python`, `pytest`, `ruff` или `mypy`
не указывают на окружение проекта, запускай команды через активированную `.venv`
или через `uv run`.

- Установка зависимостей: `make install`
- Запуск бота локально: `make run`
- Линтинг и типизация: `make lint`
- Форматирование кода приложения: `make format`
- Запуск тестов: `pytest`
- Запуск отдельного теста: `pytest tests/test_name.py`
- Эквиваленты без активированного окружения: `uv run python -m app`,
  `uv run make lint`, `uv run pytest`

## Проверки перед завершением задачи

- Для изменений в `app/` запусти `make lint`, если окружение позволяет.
- Для изменений логики запусти релевантные тесты через `pytest`.
- Если инструменты не найдены в PATH, повтори проверку через `uv run`, например
  `uv run pytest tests/test_name.py` или `uv run ruff check app/module.py`.
- Если `uv run` создал `uv.lock` только как побочный артефакт проверки, не
  добавляй его в правку без отдельного решения о lockfile.
- Если проверку нельзя выполнить, явно укажи причину в финальном ответе.
- Не добавляй новые production-зависимости без необходимости; если добавляешь,
  объясни зачем.

## Как поддерживать этот файл

- Добавляй сюда только правила, которые помогают безопасно менять именно этот
  репозиторий.
- Если правило повторяет `README.md`, `pyproject.toml` или `Makefile`, оставь
  здесь короткий практический вывод и ссылку на источник правды.
- Предпочитай маленькие уточнения: одна повторяющаяся ошибка - одно конкретное
  правило.

## Definition of Done

Задача считается завершенной, когда изменение сфокусировано, читаемо,
типизировано, не ломает существующие соглашения проекта, покрыто релевантными
тестами или честно объясняет, почему тесты не запускались.
